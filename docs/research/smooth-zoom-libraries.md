# Smooth animated zoom/pan ("Ken Burns") in programmatic video pipelines — library survey

_Research note, 2026-07-22. This file establishes the `docs/research/` convention for this repo (there was no prior research-notes location)._

**Context.** `apps/workers/worker/pipeline/render.py` renders per-scene clips with ffmpeg; scenes with a zoom go through `worker/pipeline/smoothzoom.py`, which warps every frame of a CFR-30 base clip with a float-precision `cv2.warpAffine` (INTER_CUBIC) and pipes raw frames to x264. Three implementations (ffmpeg `zoompan`; supersampled zoompan + smoothstep; current OpenCV float affine) have been tried; the camera path is now mathematically smooth, yet the user still perceives the zoom as jerky. This survey covers what other libraries do, and — more importantly — the perceptual factors that remain even with a perfect camera path.

---

## TL;DR — ranked recommendation

The current OpenCV approach is already the state of the art for _geometric_ smoothness; every serious library ends up doing the same thing (a float-precision per-frame transform followed by good resampling). What the current pipeline is missing is the _temporal_ half of the problem: **30 fps sample-and-hold judder on fast scale ramps, no motion blur, and duplicated source frames**. That is fixable in ~100 lines inside `smoothzoom.py` without adopting any new framework.

**Bottom line:** no library will out-smooth a float affine warp — they all reduce to one. The perceived jerkiness is almost certainly _temporal_ (30 fps judder + zero motion blur + frozen/duplicated source frames under a moving camera), so fix that in place (§Recommendation). If a browser-based renderer is ever wanted for richer motion design, Remotion is the most mature but has a real license cost for a company of Tarento's size; Revideo is the MIT-licensed equivalent.

## 1. Remotion

**What it is / how it renders.** React components describe frames as a function of `frame` number; the `@remotion/renderer` package opens a headless Chrome ("Chrome Headless Shell" — Remotion switched to it after Chrome removed headless mode from the desktop binary), screenshots every frame, and encodes the sequence to video. Server-side rendering from Node is three calls: `bundle()` (webpack-bundle the composition), `selectComposition()`, `renderMedia()` ([SSR API docs](https://www.remotion.dev/docs/ssr-node), [@remotion/renderer](https://www.remotion.dev/docs/renderer), [Chrome Headless Shell](https://www.remotion.dev/docs/miscellaneous/chrome-headless-shell)). Deployment options: plain Node/Bun API, Lambda, Docker, GitHub Actions, Cloud Run (alpha) ([SSR overview](https://www.remotion.dev/docs/ssr)).

**Smoothness.** An animated zoom is `transform: scale(z) translate(...)` interpolated per frame with `interpolate()`/`spring()`. CSS transforms are float-precision and Chrome's compositor antialiases the result, so the camera path is sub-pixel smooth — equivalent in quality to the current `warpAffine` approach, not better geometrically. Where Remotion _does_ add something the current pipeline lacks: **`@remotion/motion-blur`** ([docs](https://www.remotion.dev/docs/motion-blur)) provides `<Trail>` and `<CameraMotionBlur>`; `<CameraMotionBlur>` renders the children `samples` times (default 10) at sub-frame time offsets and averages them, with a film-style `shutterAngle` prop (default 180°) — i.e. true accumulation motion blur ([CameraMotionBlur docs](https://www.remotion.dev/docs/motion-blur/camera-motion-blur)). Cost: each sample is a full extra render of the subtree.

**Render speed.** Rendering = screenshotting Chrome per frame + encode; it is CPU-heavy and headless Chromium disables the GPU by default, which Remotion documents as a significant slowdown ([GPU docs](https://www.remotion.dev/docs/gpu), [performance tips](https://www.remotion.dev/docs/performance)). Real-world reports on 1080p with video layers: roughly 2–4x video duration on an 8-vCPU box, and concurrency tuning is non-obvious (`npx remotion benchmark` exists for this; more cores does not always help) — see maintainer-acknowledged issues [#4783 "Remotion is too slow to use in production"](https://github.com/remotion-dev/remotion/issues/4783) and [#4949 single-instance bottleneck](https://github.com/remotion-dev/remotion/issues/4949). Expect zoom passes to be ~5–20x slower than the current OpenCV loop (which is near-realtime).

**Licensing.** Not OSI open source. Free for individuals and companies **up to 3 people**; larger for-profit companies need a Company License ([LICENSE.md](https://github.com/remotion-dev/remotion/blob/main/LICENSE.md), [license docs](https://www.remotion.dev/docs/license)). Pricing: "Creators" $25/seat/month, or "Automators" (automated pipelines like this one) **$0.01/render with a $100/month minimum** ([pricing](https://www.remotion.dev/docs/pricing), [remotion.pro/license](https://www.remotion.pro/license)). An automated demo-video generator is squarely the "Automators" case.

**Slotting into this pipeline.** Celery task shells out to `npx remotion render <serve-url> ZoomComp --props='{"src":"base.mp4","cx":..,"cy":..,"scale":..,"easeS":..}'` (or a long-lived Node HTTP sidecar calling `renderMedia()` with a shared `openBrowser()` instance). The composition uses `<OffthreadVideo src={base}>` inside `<CameraMotionBlur>` with an animated scale. It would replace exactly the `apply_zoom()` step: base CFR clip in → zoomed clip out; captions/audio pass unchanged. Workers need Node + Chrome Headless Shell in the image.

## 2. FFCreator

Node "short video" library from Tencent NFE: renders frames with **node-canvas**, uses **headless-gl** for GL transitions on servers without a display, encodes with FFmpeg ([repo](https://github.com/tnfe/FFCreator)). Animations are TWEEN.js tweens: `FFAnimation` takes `{from, to, time, delay, ease}` with the full Tween easing set, so a continuous eased `scale` animation on an image/video element is expressible ([lib/animate/animation.js](https://github.com/tnfe/FFCreator/blob/master/lib/animate/animation.js)); the preset `effects` are animate.css-style entrance/exits (`zoomIn`, `fadeIn`, …) ([lib/animate/effects.js](https://github.com/tnfe/FFCreator/blob/master/lib/animate/effects.js)). Canvas transforms are float-based, so mechanism-wise it's the same class as the current approach. Claims "a 5 minute video only needs 1–2 minutes" ([README](https://github.com/tnfe/FFCreator)).

**Maintenance: effectively dead.** Last release v6.8.1 Feb 2023; last push Dec 2024; 180 open issues (GitHub API, checked 2026-07-22). Docs are Chinese-first. Not recommended for new adoption.

## 3. Editly

Declarative NLE in Node + ffmpeg by @mifi; decodes inputs to raw frames, composites each frame on a **fabric.js `StaticCanvas` over node-canvas** (CPU/Cairo), streams RGBA back to ffmpeg ([repo](https://github.com/mifi/editly), [src/sources/fabric.ts](https://github.com/mifi/editly/blob/master/src/sources/fabric.ts)).

**Ken Burns implementation.** `zoomDirection` (`in`/`out`/`left`/`right`) and `zoomAmount` (default 0.1) are documented "Ken Burns parameters" on image/title/image-overlay layers ([README §Ken Burns parameters](https://github.com/mifi/editly#ken-burns-parameters)). The actual math is a per-frame float scale on the fabric image — `scaleFactor = 1 + zoomAmount * progress` — i.e. **linear, no easing at all**, applied via `img.scaleToWidth(width * scaleFactor)` ([src/util.ts `getZoomParams`](https://github.com/mifi/editly/blob/master/src/util.ts), [src/sources/image.ts](https://github.com/mifi/editly/blob/master/src/sources/image.ts)). So it is float-smooth spatially but _less_ sophisticated temporally than this repo's smoothstep ease.

**Maintenance: dormant.** Last stable release v0.14.2 Dec 2022; a v0.15.0-rc.1 appeared Jan 2025; last push May 2025; 80 open issues (GitHub API, checked 2026-07-22). MIT. Nothing here this pipeline doesn't already do better.

## 4. Motion Canvas

TypeScript animation library ([repo](https://github.com/motion-canvas/motion-canvas), MIT, 18.8k stars) where animations are generator functions rendered to a Canvas 2D — float transforms, excellent easing primitives. **It is editor-centric**: rendering happens through its Vite-served web editor UI. Fully headless/server rendering is a long-open feature request — [#415 "Render projects headlessly"](https://github.com/motion-canvas/motion-canvas/issues/415) and [#1218 "Headless rendering without browser for automated pipeline"](https://github.com/motion-canvas/motion-canvas/issues/1218); community workarounds drive the editor with Puppeteer. Repo pushed Jul 2026 but the last tagged release is v3.18.0-alpha.0 (Feb 2025) (GitHub API). Not a fit for a Celery worker; if you want this programming model server-side, use its fork:

**Revideo** ([midrender/revideo](https://github.com/midrender/revideo), MIT, pushed Jul 2026, 3.9k stars) — a Motion Canvas-derived "rendering engine for creating videos in code" that "ships a headless render API (`renderVideo()`) for generating videos programmatically" plus ffmpeg-based utilities and parallel worker rendering ([README](https://github.com/midrender/revideo/blob/main/README.md), [docs](https://midrender.com/revideo/docs)). It is the MIT-licensed answer to Remotion's licensing; younger and much smaller ecosystem.

## 5. MoviePy (Python)

**Resampling.** MoviePy v2's `Resize` effect resizes each frame with OpenCV: `cv2.resize` with `INTER_LINEAR` when upscaling, `INTER_AREA` when downscaling, and — critically — **integer target dimensions** (`int(new_size[0])`) ([moviepy/video/fx/Resize.py](https://github.com/Zulko/moviepy/blob/master/moviepy/video/fx/Resize.py)). A Ken Burns move done as `Resize(lambda t: 1+k*t)` + `Crop` therefore quantizes the frame size per frame, which is exactly the classic jitter:

- [Issue #183 "Zoom effect trembling"](https://github.com/Zulko/moviepy/issues/183) (2015) — slow zoom-in on stills produces shaky output.
- [Issue #1402 "Zoom-In Effect for moviepy"](https://github.com/Zulko/moviepy/issues/1402) (2021) — diagnoses the integer/even-dimension rounding; never fixed in core.
- The canonical community fix ([mowshon's gist](https://gist.github.com/mowshon/2a0664fab0ae799734594a5e91e518d5)): supersample (resize to a larger intermediate), center-crop, then downsample with **PIL LANCZOS**, keeping dimensions even.

So MoviePy would be a _regression_ versus the current float `warpAffine` (which never changes frame dimensions and has no per-frame integer rounding). Speed is also poor: pure-Python per-frame loop plus ffmpeg pipe, generally slower than the current cv2 loop. Active project though: v2.2.1 released May 2025, repo pushed Mar 2026 (GitHub API). Only relevant as confirmation that this repo's approach (float affine at fixed output size) is the correct fix for the geometric problem.

## 6. PyAV / pure OpenCV (current approach) — remaining tricks

The current `smoothzoom.py` already has: float camera path, smoothstep easing, INTER_CUBIC, CFR input. Additional, orthogonal levers:

1. **Interpolation filter.** OpenCV offers `INTER_LANCZOS4` (8x8 Lanczos) in `warpAffine`/`resize` ([OpenCV InterpolationFlags](https://docs.opencv.org/4.x/da/d54/group__imgproc__transform.html#ga5bb5a1fea74ea38e1a5445ca803ff121)). For _upscaling_ (zoom-in) Lanczos is slightly sharper than cubic but also rings more on hard UI edges/text; it will not change perceived judder. More impactful for text shimmer: **supersample the warp** — warp into a 2x buffer and reduce with `INTER_AREA` — which antialiases the moving text edges that otherwise scintillate frame-to-frame.
2. **Accumulation motion blur (the big one).** Do what Remotion's `<CameraMotionBlur>` does ([docs](https://www.remotion.dev/docs/motion-blur/camera-motion-blur)): during the ease ramps, compute the affine at N sub-frame times (e.g. N=4 across a 180° shutter, i.e. offsets spanning half the frame interval), warp N times, average the results. Cost is N warps/frame only while z is changing. This converts discrete "steps" of the zoom into directional smear, which is precisely what eyes read as "smooth camera" — film has always relied on it.
   - Cheap ffmpeg-side variant: render the zoom at 120 fps and reduce to 30/60 with the [`tmix`](https://ffmpeg.org/ffmpeg-filters.html#tmix) filter (averages successive frames); [`minterpolate`](https://ffmpeg.org/ffmpeg-filters.html#minterpolate) can synthesize in-between motion but is slow and artifacts badly on UI content.
3. **Render at 60 fps.** See §Perceptual factors — the single biggest lever for fast ramps. The OpenCV loop trivially supports it (interpolate the affine at 60 Hz; the base clip's 30 fps frames are just sampled twice, but the _camera_ moves every frame, which is what matters).
4. **Gamma-correct scaling.** Resampling in gamma-encoded sRGB (what `warpAffine` on BGR bytes does) darkens/pulses fine bright-on-dark text during scale changes — the classic "gamma error in picture scaling" ([Eric Brasseur's reference article](http://www.ericbrasseur.org/gamma.html)). Converting to linear light (float32), warping, converting back removes a subtle brightness shimmer on screen-recording text. Second-order effect; try after (2) and (3).
5. **Cap zoom velocity.** Perceived judder scales with pixel displacement per frame. At 1080p/30 a 1.0→1.6 zoom in 0.4 s ("speed 5" ⇒ `ease_s=0.4` in `render.py:_zoom_ease_s`) moves edge content ~30 px/frame — guaranteed strobing without blur. Enforce a max px/frame at the frame edge and stretch `ease_s` to fit.

## 7. Perceptual factors no library fixes

- **Sample-and-hold judder.** Modern displays hold each frame for its full interval; when the eye tracks a moving edge, a 30 fps hold means the edge is "wrong" for 33 ms at a time — perceived as stutter/strobing on fast motion even when the motion path is mathematically perfect. Low frame rate content has this inherently ("a 24fps movie shows only 24 unique moments per second"); higher fps or motion blur are the only remedies ([Blur Busters sample-and-hold explainer](https://blurbusters.com/faq/oled-motion-blur/), [Blur Busters forum: judder in low framerate content](https://forums.blurbusters.com/viewtopic.php?t=14487)). This is the most likely reason the user still calls the mathematically-smooth zoom "jerky": during the ease ramps the per-frame displacement is large and each sharp frame is held.
- **Motion blur hides cadence.** Camera/synthetic motion blur softens each frame along the motion vector so the held frames blend perceptually; removing blur exposes the cadence (same source as above — motion-blur-_reduction_ modes make 24/30 fps content look _more_ juddery). Hence Remotion ships `<CameraMotionBlur>`/`<Trail>` as multi-sample averaging ([docs](https://www.remotion.dev/docs/motion-blur/camera-motion-blur)) — and the same technique drops into the OpenCV loop.
- **Duplicated source frames under a moving camera.** The macOS screen recordings are VFR/low-fps; after CFR-30 normalization, consecutive output frames often carry the _same_ source image. A perfectly smooth camera over a frozen image reads as smooth; the jarring case is the mix — content that updates at ~10–15 Hz _while_ the camera moves at 30 Hz produces two competing cadences. Mitigations: prefer zooming during static holds (already partially true since zooms anchor on clicks), and motion blur on the camera axis to mask the content cadence.
- **Browser playback drops.** The editor previews via `<video>`; browsers silently drop frames under load, which users report as "jerky render". This is measurable: `HTMLVideoElement.getVideoPlaybackQuality()` exposes `droppedVideoFrames`/`totalVideoFrames` ([MDN VideoPlaybackQuality](https://developer.mozilla.org/en-US/docs/Web/API/VideoPlaybackQuality)). Worth instrumenting the web player before attributing further jerkiness to the renderer — a 1080p60 or high-bitrate CRF-18 stream can drop frames on weak machines where the file itself is perfect (verify by stepping frames in QuickTime/mpv).
- **Easing shape.** Smoothstep has zero velocity but _discontinuous acceleration_ at the ends of each ramp is avoided (C1 only); a quintic smootherstep (C2) or an exponential-decay ("camera chase") profile reads slightly more organic on hold-transitions. Minor next to fps/blur.

## 8. Other options (brief)

- **Diffusion Studio `@diffusionstudio/core`** ([repo](https://github.com/diffusionstudio/core)) — TypeScript, **browser-based** engine on Canvas2D + WebCodecs, keyframing included; MPL-2.0; YC F24 company. Server use means running it inside headless Chrome anyway, so it buys nothing over Remotion/Revideo for this pipeline. v2.0.0 Feb 2025, pushed Nov 2025.
- **etro.js** ([repo](https://github.com/etro-js/etro)) — browser canvas video framework, GPL-3.0 (viral for a SaaS), active (v0.14.0 Jun 2026) but browser-oriented; not a server pipeline fit.
- **gl-transitions** — shader _transitions between clips_, not continuous camera moves; not applicable to a within-clip Ken Burns.
- **Hosted render APIs**: [Shotstack](https://shotstack.io) ships preset `zoomIn`/`zoomInSlow`/`zoomInFast` motion effects (fixed 1→1.1/1.3/1.7 scales; depth not freely tunable — [community thread](https://community.shotstack.io/t/zoomin-effect-with-setting-the-zoom-depth/268), [Ken Burns template](https://shotstack.io/templates/ken-burns-effect-slideshow-fast/)); [Creatomate](https://creatomate.com/docs) is a similar JSON-to-video SaaS. Both mean shipping customer screen recordings to a third party, per-render fees, and less control than the in-house warp — only interesting if the whole render pipeline were outsourced.
- **manim** — mathematical animation engine; renders its own scenes, has no notion of warping an existing video under a camera; wrong tool.

## Recommendation for this repo

### Top pick: keep the OpenCV warp, add the temporal layer (no new framework)

The geometric problem is solved; the remaining jerkiness matches the sample-and-hold + no-blur + fast-ramp signature. Concretely, in `apps/workers/worker/pipeline/smoothzoom.py`:

1. **Sub-frame accumulation blur** in `apply_zoom`: when `|z(t+dt)-z(t)|` exceeds a threshold, evaluate the affine at N=3–5 offsets across a 180° shutter (`t + k/(N)·0.5/fps`), `cv2.warpAffine` each, average with `cv2.addWeighted`/numpy mean. Frames in the hold phase stay single-sample (sharp), ramps get smeared — exactly Remotion's `<CameraMotionBlur>` semantics ([docs](https://www.remotion.dev/docs/motion-blur/camera-motion-blur)) at a fraction of the cost.
2. **60 fps through the zoom path**: raise `FPS` handling so zoom segments render at 60 (the base-clip pass in `render.py:_render_segment` already does `fps={FPS}`; the concat pass re-encodes, so make the _whole_ output 60 fps — mixed-fps concat inputs are fragile). 1080p60 CRF-18 roughly doubles encode time and file size; if that's unacceptable, keep 30 fps output and rely on (1), which is precisely what film does at 24 fps.
3. **Velocity cap**: derive `ease_s` from a max edge displacement (~8–12 px/frame at 30 fps, ~16–24 at 60) instead of the fixed speed table in `render.py:_zoom_ease_s`, so "snappy" can never outrun the frame rate.
4. Optional polish: 2x supersampled warp + `INTER_AREA` reduction for text-edge stability; smootherstep easing.

This slots into the existing per-segment flow untouched: base CFR clip → (upgraded) `apply_zoom` → captions/elements/audio pass. Segment caching (`clip_hash`) keeps working; bump the `"v9"` hash tag.

### Runner-up: Remotion as a zoom/motion render service

If the product later needs browser-grade motion design (springy camera, overlays, cursor animations), stand up a Node sidecar: `bundle()` once at deploy, then per segment `renderMedia({composition: "ZoomPass", inputProps: {src, cx, cy, scale, durS, easeS}, codec: "h264"})` ([SSR API](https://www.remotion.dev/docs/ssr-node)) with `<OffthreadVideo>` inside `<CameraMotionBlur>`. Celery calls it over HTTP or `npx remotion render`; it replaces only the `apply_zoom` step, same clip-in/clip-out contract. Costs: Chrome Headless Shell + Node in the worker image, ~2–4x realtime renders ([#4783](https://github.com/remotion-dev/remotion/issues/4783)), and the **Automators license ($0.01/render, $100/mo minimum)** since Tarento exceeds the 3-employee free tier ([pricing](https://www.remotion.dev/docs/pricing)). If the license is a blocker, **Revideo** ([MIT, headless `renderVideo()`](https://github.com/midrender/revideo)) is the drop-in-philosophy alternative, with a smaller ecosystem.

Avoid: Editly and FFCreator (dormant, and their zoom math is simpler than what this repo already has), MoviePy (integer-dimension resize is the very jitter bug being escaped), Motion Canvas proper (no supported headless path).
